# 01 定位与目标

## 1. 问题陈述

2026 年 AI 应用的落地瓶颈已经从"模型不够强"转移到"结果不可控"。可观测性基本普及，但闭环质量保障几乎空白：

- **89%** 的团队已经为 agent 实现了观测能力 —— trace 采集不再是差异化能力。
- 只有 **52.4%** 做离线评测，**37.3%** 做在线评测，**29.5%** 完全没有任何评测。
- 质量问题被列为生产事故的首要原因，但绝大多数团队的处理方式仍是"人看 trace、人改 prompt、人重跑"。

这里存在一个结构性缺口：**评测发现了问题，但没有任何机制自动修复问题。** 现有平台把 eval 分数呈现给人，闭环的最后一环（改 → 验 → 再改）由人手工完成，这是最贵也最不可扩展的一环。

同时，早期 Agent 框架（AutoGPT 一代）暴露了另一个致命问题：**模型说"我完成了"就停了，但任务远未达标。** 模型的自我评估不可信，需要外部机制强制裁决。

## 2. 产品定位

Ariadne = **Loop Engineering 运行时** + **质量保障**（评测 + 硬约束）+ **可观测性底座**。

三者的关系不是并列，而是层层支撑：

```
可观测性（采集事实）→ 评测（把事实变成分数与断言）→ Loop（用断言驱动自动迭代）
```

因此项目的重心是最上层。观测和评测做到"够用且开放"，不与 Langfuse / Phoenix 拼采集功能的广度；差异化全部押在**闭环自动修复**上。

## 3. 目标用户与核心场景

| 用户 | 痛点 | Ariadne 提供的价值 |
|---|---|---|
| **AI 应用开发者**（个人 / 小团队，构建 agent、RAG、内容生成） | 输出质量抖动大，改 prompt 靠猜，回归无从验证 | 设定可验证目标，Loop 自动迭代到达标；每轮改动与得分变化可视化 |
| **平台 / 基础设施团队**（为公司内多个 AI 应用提供统一底座） | 无法给业务方设"质量闸门"，成本与失败率不可控 | Harness 硬约束 + 预算熔断 + SLO 错误预算告警；多租户隔离 |
| **批量内容 / 数据处理场景**（生成 N 篇文档、处理 N 个文件） | 逐个人工检查不可行，失败项需要重试并留痕 | 并行 Loop 池 + 断点续跑 + 逐项验证报告 |

三个高价值切入场景（首版优先支持）：

1. **代码生成与修复**：验证信号最硬（编译通过、测试通过、lint 通过），Loop 收敛效果最明显，适合作为标杆场景。
2. **结构化内容生成**：技术博客、报告、营销文案，用"引用必带 + 格式校验 + 质量评分阈值"作为断言。
3. **RAG 问答质量治理**：检索命中率、事实性、引用一致性作为多维断言，不达标自动改写 query 或换检索策略后重试。

## 4. 明确的非目标

写清楚不做什么，比写做什么更能保护项目不失焦：

- **不做模型训练 / 微调平台**。Ariadne 只在推理侧工作。
- **不做通用 APM**。不采集 HTTP/DB/基础设施指标，只覆盖 AI 工作流链路；需要全栈关联时通过 trace_id 与既有 APM 打通。
- **不做模型网关（LLM Gateway）**。不做统一转发、负载均衡、密钥托管代理。可与 LiteLLM 等网关并存。
- **不做 prompt 市场 / 模板商城**。Prompt 版本管理只做到"可复现实验"所需的最小集。
- **首版不做多 Agent 协作编排**。单工作流的 Loop 闭环先做透，多 Agent 编排留到里程碑 M6 之后评估。
- **不追求覆盖所有框架的自动埋点**。首版只保证 OpenAI SDK / Anthropic SDK / LangChain / LangGraph 四条主链路。

## 5. 成功指标

### 5.1 北极星指标

**闭环达标率（Closed-Loop Success Rate）**：在预算约束内，Loop 把不达标输出修正到达标的比例。这是唯一能证明"自动修复"价值的指标，目标 ≥ 70%（代码类场景 ≥ 85%）。

### 5.2 产品指标

| 指标 | 目标 | 说明 |
|---|---|---|
| 首次接入耗时 | ≤ 30 分钟 | 已有 LangChain/OpenAI 应用接入并看到完整三视图 |
| 平均达标轮次 | ≤ 3 轮 | 超过 3 轮说明反馈信号质量不足 |
| 假完成拦截率 | ≥ 95% | 模型声称完成但断言未过的情况被 Ralph Verifier 拦住 |
| 单次达标成本增幅 | ≤ 2.5× | 相对单轮直出的成本倍数，超过说明 Loop 不经济 |

### 5.3 技术指标

| 指标 | 目标 |
|---|---|
| SDK 同步路径开销 | < 1 ms（异步批量上报，不阻塞业务） |
| 单实例 Collector 吞吐 | ≥ 5,000 spans/s |
| Trace 查询 p95（1 亿 span 规模） | < 500 ms |
| SSE 状态推送延迟 | < 200 ms |
| Loop 崩溃恢复 | 从最近检查点续跑，不重复已完成轮次 |

### 5.4 反向指标（守住不能退化的东西）

- Loop 因预算熔断而终止的比例 < 10%（过高说明目标设计不合理或反馈无效）。
- Judge 与人工标注的 Cohen's κ ≥ 0.6（低于此值 LLM-as-Judge 的分数不可作为断言依据）。
- 平台自身引入的 P95 额外延迟 < 50 ms。
